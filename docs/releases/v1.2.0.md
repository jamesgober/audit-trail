# Release v1.2.0 - Pre-1.0 review
**Date:** 2026-11-04
**Compare:** `v1.1.0...v1.2.0`

## Summary

A security and edge-case review of the whole crate, run before the
suites that use it reach 1.0. No public API change, and the wire format
and every existing hash are unchanged (a test pins them). It is a minor
release because some inputs 1.1.0 accepted are now refused, and `libc`
is a new dependency on Unix.

## Security

- **Field boundaries in the hash.** Fields are separated by `0x1f`
  without a length prefix, so text could move between fields without
  changing the hash. `Chain::append` refuses a field containing `0x1f`,
  and `Verifier::verify` refuses such a record (`Error::InvalidFormat`).
- **Reader allocation.** A length prefix claiming 4 GiB no longer makes
  `FileReader` allocate 4 GiB before reading; the buffer grows with the
  bytes actually read. The same prefix no longer panics on 32-bit
  targets.
- **One writer per file.** With Rust 1.89 or later (the MSRV stays
  1.85), `Chain::open_file` holds an exclusive lock on `<path>.lock`, so
  a second writer in any process fails instead of interleaving. A file
  that grows while it is verified is refused in every build.
- **Links and permissions.** `open_file` and
  `FileSink::open_or_create_private` do not follow a symbolic link at
  the path, and `open_file` accepts only a regular file. On Unix a file
  others can read is made owner-only, and one others can write is
  refused.
- **No write behind a torn record.** After an I/O error `FileSink`
  refuses every later write, so a retry cannot land behind a partial
  record where repair cannot reach it.

## Fixed

- A file cut inside a length prefix, a tail of zeros from a crash, and a
  file cut inside its header are all `Error::Truncated` now, and the
  repairing open cuts them.
- A second repair at the same offset no longer fails on an existing cut
  file, and the repair streams the tail instead of reading it into
  memory.
- `--no-default-features` builds of the benches and one test compile
  again.

## Changed

- A created chain file's header is synced with its directory entry
  (Unix), and so is a cut file's.
- `open_file` decodes records in place: no allocation per record, a
  10 000-record chain opens in 1.6 ms instead of 2.6 ms on the dev host.
- The docs state what a chain proves and what it cannot see on its own
  (records removed from the end, a rewrite by someone who can recompute
  unkeyed hashes), with the defences.

## Upgrading

Nothing to change in code. A chain written by an earlier version
verifies unless one of its fields holds the byte `0x1f`. A program that
opened its chain file through a symbolic link, or kept it writable by
others, gets an error at open and must fix the path or the mode.

# Benchmark Baselines — v0.9.0

**Captured:** 2026-05-20
**Host:** Windows 11, Rust 1.95 stable, release profile (LTO=fat, codegen-units=1).
**Mode:** `cargo bench --all-features -- --quick` (3 samples per bench).

Numbers are wall-clock medians from criterion. They are not portable
across hardware — what matters is the *ratio* between hashers and the
*shape* of regressions on subsequent releases.

## `append` (per call)

Single `Chain::append` invocation: clock read, id alloc, canonical
encoding, hash, sink write, state update.

| Hasher       | Median  | Δ vs XOR   |
|--------------|---------|------------|
| XorHasher    | 127 ns  | (baseline) |
| Sha256Hasher | 176 ns  | +49 ns     |
| Blake3Hasher | 294 ns  | +167 ns    |

## `verify` (1 000 records)

Full chain replay through `Verifier::verify`. Cost is dominated by the
hash itself once per record, plus the canonical re-encoding and three
fixed-size comparisons.

| Hasher       | Median   | Per-record  |
|--------------|----------|-------------|
| XorHasher    | 15.5 µs  |   15.5 ns   |
| Sha256Hasher | 71.1 µs  |   71.1 ns   |
| Blake3Hasher | 194 µs   |  194 ns     |

## Observations

- **The XOR baseline isolates the non-hash overhead** of `append` (about
  127 ns) and `verify` (about 15.5 ns per record). This is the floor any
  cryptographic hasher must add on top of.
- **For our small input size (~100 bytes per record), SHA-256 beats
  BLAKE3.** This is the expected pattern: BLAKE3's parallelism wins on
  larger payloads (kilobytes+), but its per-call setup cost dominates
  for tiny inputs. SHA-256 on modern x86_64 has hardware acceleration
  (`SHA-NI`); BLAKE3 here is software-only.
- **Numbers are not regressed against a prior baseline** — this is the
  first baseline. Future releases should compare to these targets.

## How to reproduce

```bash
cargo bench --all-features -- --quick
```

Drop `--quick` for full criterion runs with HTML reports.

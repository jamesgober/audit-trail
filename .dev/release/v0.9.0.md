# Release v0.9.0 — Feature Freeze & Pre-1.0 Audit
**Date:** 2026-05-20
**Compare:** `v0.7.0...v0.9.0`

## Summary

`v0.9.0` is the audit milestone. No new public features land in this
release; instead, every public surface is reviewed against the pre-1.0
checklist in `.dev/ROADMAP.md` and any gaps are closed. `v1.0.0` will
follow once this commit is green across the cross-platform CI matrix
on both `stable` and the declared MSRV.

The audit pass turned up only minor gaps — a missing `# Errors`
section on `codec::encode_record`, an undocumented `#[allow]` on
`Record::new`, and a handful of error variants that were defined but
not exercised by tests. All closed in this release; the public API
itself was clean going in.

A first benchmark baseline was captured so future releases can detect
regressions against a concrete number.

The single `#[allow(clippy::too_many_arguments)]` lives on

### API stability

| Item                            | Decision                                         |
|---------------------------------|--------------------------------------------------|
| `Hasher` / `Sink` / `Clock`     | Intentionally **open** — the point is pluggability |
| `Error` / `SinkError` / `Outcome` | `#[non_exhaustive]` (variants likely to grow)   |
| `Record` / `OwnedRecord`        | Public 5W + chain links shape; fields stable    |
| `Digest` / `Timestamp` / `RecordId` | Newtype wrappers around fixed primitives    |
| Wire format (`codec`)           | Stable; embeds 1-byte `FORMAT_VERSION`           |

No trait was sealed: every trait in this crate is meant to be
implemented externally. No `#[non_exhaustive]` was added or removed.

### Error hardening

- Every public function returning `Result` now has a `# Errors`
  rustdoc section: `Chain::append`, `Verifier::verify`,
  `codec::encode_record`, `codec::decode_record`,
  `codec::verify_file_header`, `FileSink::open_or_create`,
  `FileSink::flush`, `FileReader::open`, `Sink::write` (trait-level).
- Every `Error` and `SinkError` variant now has a `Display` test
  asserting its exact error message. Adding a variant without a
  Display arm now fails the lib test suite, not just the compiler.
- `Error::source` chains through `Error::Sink → SinkError` (verified
  in a unit test under the `std` feature).
- `From<SinkError> for Error` roundtrip tested.
- No `panic!` / `unwrap` / `expect` / `todo!` / `unimplemented!` in
  shipping code paths. The only such tokens in `src/` appear inside
  `///` doctest blocks (idiomatic).

### Performance

First-ever captured baseline lives at
[`.dev/benchmarks/v0.9.0-baseline.md`](../benchmarks/v0.9.0-baseline.md).

Summary (Windows 11, Rust 1.95 stable, release profile):

| Bench (per-call) | XOR (baseline) | SHA-256 | BLAKE3 |
|------------------|----------------|---------|--------|
| `append`         | 127 ns         | 176 ns  | 294 ns |
| `verify` (×1000) | 15.5 µs total  | 71.1 µs | 194 µs |

Notable: **BLAKE3 is slower than SHA-256 on this workload.** BLAKE3's
parallelism amortises on kilobyte+ payloads; for ~100-byte audit
records the per-call setup dominates, and modern x86_64 has SHA-NI
hardware acceleration that BLAKE3 here cannot use. SHA-256 remains
the recommended choice for typical audit-trail use cases.
